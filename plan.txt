A phased implementation plan and key engineering best practices for building the Reactor Historian Simulator ensure clean data integrity, predictable delivery, and minimal rework.

**Implementation Plan**

* **Phase 1: Database Foundation & Schema Setup**
* Set up PostgreSQL with TimescaleDB hypertables for raw readings (`timestamp`, `tag`, `value`, `quality`), batches, events, and rollups.


* Implement automated retention policies (90 days for raw data, 2 years for rollups) and chunk compression.


* Create continuous aggregates for 1-minute rollups.




* **Phase 2: Simulation Engine & Seeding Mechanism**
* Implement the state machine for the 3 reactors and 7 batch phases (`Idle`, `Charging`, `Heating`, `Hold`, `Cooling`, `Discharge`, `Clean`).


* Implement the PRNG-based synthetic generator to produce deterministic data.


* Build the fast-backfill seeding script to populate 90 days of synthetic batch history on startup.


* Establish the 1-second calculation tick and 5-second database persistence loop.




* **Phase 3: Backend REST API & Real-Time Push Layer**
* Build the core REST endpoints for the 5 BatchLine EBR use cases (single value, event times, summary calculations).


* Implement WebSocket or Server-Sent Events (SSE) to broadcast live readings every 1–2 seconds to clients.


* Create the outbound background worker for periodic monitoring push jobs (fixed duration and manual completion).


* Add the simulation control endpoints (pause/resume, fault injection, phase forcing).




* **Phase 4: Frontend Development**
* Set up the base dashboard shell (sidebar navigation, persistent header with simulation clock/state).


* Build the **Plant Overview** (card layout, vessel visuals, 24h phase lane, event feed) and **Reactor Detail** screens (animated vessel, multi-axis trends).


* Build the **Trend Explorer** (tag tree, resolution switching, full-precision data table, summary strip).


* Implement **Batches & Events**, **Monitoring Jobs**, and **Simulation Control** screens.




* **Phase 5: Validation & Deployment**
* Configure the multi-container `docker-compose.yml` (Frontend, API, Engine, TimescaleDB, Grafana, Reverse Proxy).


* Run validation checks against mock BatchLine integration calls.

**Best Practices**

* **Database & Time-Series Optimization**
* **Hypertables and Chunk Sizing:** Partition TimescaleDB hypertables by time with chunk intervals tuned to match your write rate (e.g., 7-day or 14-day chunks for ~200k rows/day).


* **Continuous Aggregates:** Do not compute 1-minute and 1-hour rollups on-the-fly for wide time ranges; use TimescaleDB Continuous Aggregates to guarantee sub-second queries on the Trend Explorer.


* **Quality Flags as Enums:** Store quality indicators (`Good`, `Questionable`, `Bad`, `Substituted`) as compact integers or enums to save disk space and index overhead.




* **Architecture & Simulation Decoupling**
* **Separate Engine from Web Server:** Keep the simulation loop in a separate Node.js process/container as specified. An intensive API query or CSV export must never block the 1-second simulation tick or 5-second persistence interval.


* **Deterministic Seeding:** Ensure your pseudo-random number generator (PRNG) is strictly seed-based. If an integration test fails, developers should be able to reproduce the exact dataset by reusing the seed.




* **Data Integrity & Traceability (EBR Compliance)**
* **Never Round Database Values:** Store and serve sensor values with exact double-precision floating points. Leave rounding solely to UI presentation layer formatting.


* **Time-Weighted vs. Event-Weighted:** Accurately implement both averaging formulas for event summaries, as chemical batch validation relies strictly on trapezoidal time-weighted averages over varying sample gaps.


* **Handle Gaps Accurately:** When visualising time series, render `Bad` quality flags as blank gaps in the charts rather than interpolating between them, ensuring engineers are not misled by false measurements.




* **UI & Performance**
* **Canvas/WebGL Charting:** Use a high-performance, canvas- or WebGL-based charting library (such as uPlot, Apache ECharts, or Chart.js) to smoothly handle multi-parameter streaming at 1–2 second intervals without UI lag.


* **Strict Query Guardrails:** Enforce hard row limits and time-window restrictions on historical queries in the API so large range queries cannot exhaust server memory.

Milestones

1. Schema and the simulation core (the largest and most important piece)

Docker Compose with Postgres, Timescale, and Grafana. Create the tables: assets, tags, readings hypertable, batches, events. Then write the phase state machine and the coupled process model as pure functions, driven by a seeded PRNG. Run it in fast mode to generate 90 days.

Done when: GET nothing, but a SQL query returns a couple of hundred completed batches with plausible curves.

2. Look at it in Grafana

Before building any UI. Point Grafana at Timescale, throw up a four-parameter trend panel with phase boundaries, and stare at it. This is the cheapest possible instrument for validating that your heating ramp overshoots correctly, that pressure tracks temperature, that volume steps cleanly. Fix the model here, where fixing it costs nothing.

Done when: a batch looks like something a process engineer would recognise.

3. Live loop and stream

Switch the same engine to realtime, writing every 5 seconds and pushing every 1 to 2. Express plus a WebSocket endpoint. Test with wscat, no browser.

Done when: values advance continuously and survive a process restart without a gap in the archive.

4. Read API, cases 1 to 3

Write the OpenAPI spec first, then implement. Event frame search, single value with retrieval modes, summary with time-weighted average and percentGood, crossings. Publish the Swagger UI.

Done when: you can answer "max temperature during the Heating phase of batch B-2026-0142" in two curl calls, and the number matches what Grafana shows.

5. Frontend, overview and reactor detail

Now the mockups have data to bind to. These two screens carry your demo.

Done when: someone unfamiliar with the project understands the plant state in ten seconds.

6. Batches, events, and trend explorer

The verification path. Exact values, copyable timestamps, quality badges.

Done when: you can trace a number from an API response back to a row in the table.

7. Monitoring jobs, cases 4 and 5

Jobs table, scheduler, outbox, idempotency keys. Write a stub BatchLine receiver yourself first, one that can be told to fail, so you can prove retry behaviour before the real integration.

Done when: a job survives you killing the API mid-sample and delivers exactly once.

8. Simulation control and fault injection

Last, because until now you've been forcing conditions by editing code. This screen makes that a UI action.

Steps 1 to 4 are roughly half the calendar time and nearly all the risk. Step 7 is the biggest single chunk of remaining work.
